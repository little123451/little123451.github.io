## 1. 现状摘要

### 1.1 一句话

培育是**确定性流水线**：两只个体放进栏位 → `pen.breed` 按天累加 → 满 2.5 天结算一次 → 产蛋 / 等蛋位 / 力竭死 / 争斗死 四选一。全程没有成功率随机数。

### 1.2 结算链路

```
main.mjs rAF
  └─ L.tick(state, dtDays)                          logic.mjs:1384
       ├─ 被动经验（栏内 26/s，围栏 7/s）            :1405-1417
       ├─ 实验室挣扎 -2/天                           :1419-1426
       ├─ 培育栏：pen.breed += dtDays                :1428-1439
       │     └─ resolvePen()                         :1283-1358
       ├─ 孵化：daysLeft -= dtDays → hatch()          :1441-1445
       ├─ 自动喂食器                                 :1447-1462
       ├─ 围栏霸凌                                   :1464-1474
       └─ 耐受归零清算                               :1476-1498
  └─ UI.handleEvents(events) → toast/日志/动画      ui.mjs:159-176
  └─ 每 120ms UI.render()：ensure*（建结构）+ patch*（刷数值）
```

#### A2 喂食器真正升级（P0-2）

> ⛔ **最终没有按本方案修，而是整件删除。**
> 决策：自动喂食器只作用于培育栏、且设计上"喂糖"应该是一次手动决策，自动喂食把这个决策取消了。
> 已移除：`UPGRADE_INFO.feeder`、`state.upgrades.feeder`、`state.feederTimer`、tick 里的自动喂食块，以及测试里的设施表条目。
> 下面保留原方案作为历史记录。

把「先 `exp += 40` 再 `gainExp(..., 0, ...)`」改成一次正常结算：

```js
// 现在
target.exp += 40;
gainExp(state, target, 0, events);
// 改为
gainExp(state, target, 40, events);
```

- **注意**：`gainExp` 的 `while (guard++ < 80)` 上限对「一帧内多次喂食」是安全的；但喂食器每 6–14 秒才触发一次，单次 40 经验不会连升多级。
- **测试**：新增「喂食器让栏内个体升级并提升耐受上限」「喂食器不碰围栏/实验室个体」。
- **风险**：低。但会让挂机玩家升级变快（这正是功能本意）。

#### A3 繁育条跨 tick 补结算（P0-3）

让 `resolvePen` 返回结果类型，`tick` 内循环结算，直到进度不足阈值：

```js
// resolvePen 改为 return { kind: 'egg' | 'waiting' | 'exhausted' | 'fight' | 'sterile' | 'locked' | 'none' }
// tick 中：
pen.breed += dtDays;
let guard = 0;
while (pen.breed >= CONFIG.breedDays && guard++ < 40) {
  const res = resolvePen(state, pen, events, i);
  if (res.kind === 'waiting' || res.kind === 'none') break;  // 蛋位满/异常，停止
  pen.breed -= CONFIG.breedDays;                             // 保留溢出进度
}
```

- 同时修掉「新造的蛋被同一 tick 瞬孵」：把孵化循环用 `dtDays` 之外的时间轴，或对**本 tick 新造**的蛋跳过扣减（记录 `egg.bornDay = state.day` 后比较）。
- **测试**：test-logic.mjs:711-723（100 耐受 ≈ 3 只）必须仍成立——3 次产蛋后第 4 次判力竭，逻辑不变；新增「tick(10) 一次补出多枚蛋」「同一 tick 不瞬孵」。
- **风险**：中。`resolvePen` 返回值是内部契约，改动面在 `tick` 一处；建议同时把「等待蛋位时 `breed = breedDays`」改成显式 `waiting` 语义。

#### A4 数据兜底与封装收口（P0-4/5/6）

- `stats.bred/hatched` → `(state.stats.bred || 0) + 1`。

- **测试**：新增「出售/交付后栏位进度为 0」「构造缺字段的 stats 不产生 NaN」。
- **风险**：低。

**A 包合计**：约 120–180 行改动，新增 10–14 条测试。

### B. 契约包：兼容性判定单一实现（P1-2）

**目标**：把「条满会发生什么」的判断收进 `logic`，UI 只消费、不重算。

```js
// logic.mjs 新增（内部真相源）
export function penOutcome(state, pen) {
  const a = monByUid(state, pen.a), b = monByUid(state, pen.b);
  if (!a || !b) return { kind: 'idle' };
  if (a.dexId !== b.dexId && failedPair(state, a.dexId, b.dexId)) return { kind: 'locked', a, b };
  const comp = compatibility(state, a, b);
  if (comp.ok) {
    if (state.eggs.length >= eggSlots(state)) return { kind: 'waiting-egg', a, b };
    const bearer = breedCostBearer(a, b);
    if (bearer.tolerance - CONFIG.breedToleranceCost <= 0) return { kind: 'will-die', a, b, bearer };
    return { kind: 'will-breed', a, b, bearer };
  }
  if (comp.sterile) return { kind: 'hopeless', reason: comp.reason, a, b };
  return { kind: 'will-fight', a, b, weak: weakerOf(a, b)[0], strong: weakerOf(a, b)[1] };
}
```

- `resolvePen` 变成 `penOutcome` 的 `switch` 执行器；`assignPen` 的黑名单检查改调 `failedPair`（已一致）；UI 的 `patchPens` 只读 `penOutcome`。
- **关键约束**：UI **只允许**外泄 `waiting-egg` / `locked` / `hopeless` 三种状态；`will-breed` / `will-fight` 必须保持沉默，否则违反 test-ui.mjs:97-98 的「只能靠试」设计。
- **测试**：新增 `penOutcome` 的全状态单测；UI 断言「蛋位满显示提示」「锁定的对显示提示」「不显示可以配种」。
- **风险**：低-中（纯重构，行为不变）。建议**先**做 B 再做 F，否则 F 会再造一份重复判断。

### C. 亲缘与家谱（P1-1）— 本次唯一的"新机制"

**目标**：让「培育」有长期策略，而不是无限自交。

#### C1 数据

| 字段 | 位置 | 内容 |
|---|---|---|
| `egg.parents` | 蛋 | `[{ uid, dexId }]`（买来的蛋为 `[]`） |
| `egg.ancestors` | 蛋 | 父代祖先 uid 并集（含父母本身），上限 8 |
| `mon.ancestors` | 个体 | 同上，孵化时从蛋继承 |
| `mon.gen` | 个体 | 代数：`1 + max(父母 gen)`，买来的为 0 |

理由：只存 uid 就够做亲缘判定，且父母被放生也不影响；上限 8 覆盖到曾祖辈，内存可忽略（每只 ~8 个短字符串）。

#### C2 判定

```js
export function isKin(a, b) {
  if (!a || !b) return false;
  const A = new Set(a.ancestors || []);
  const B = new Set(b.ancestors || []);
  if (A.has(b.uid) || B.has(a.uid)) return true;      // 亲子
  for (const u of B) if (A.has(u)) return true;        // 兄妹 / 更远的共同祖先
  return false;
}
```

#### C3 惩罚形态（**需拍板**，见 D1）

| 选项 | 规则 | 优点 | 代价 |
|---|---|---|---|
| K1 仅标记 | 栏位与详情显示「近亲」，无数值影响 | 零风险，先把数据跑起来 | 没有玩法压力 |
| **K2 耐受与体质（推荐）** | 近亲配对：承担方成本 32 → 48；后代 `toleranceCap × 0.8`（新增 `createMon` 的 `toleranceFactor` 选项） | 与现有耐受度系统天然咬合，"血统"变成资源 | 需要新增 `toleranceFactor` 与测试 |
| K3 禁配 | `compatibility` 直接返回 `code:'kin'`，不产蛋不争斗 | 最直白 | 玩家容易卡住；与"只能靠试"的设计冲突 |

- 建议：**K2 + 栏位显示「近亲」**，惩罚温和且可感知。
- **测试影响**：现有 fixture 全是互不相关的个体，默认不触发；新增「兄妹判定」「亲子判定」「近亲后代耐受 ×0.8」三组用例。
- **存档**：直接加字段；按项目约定不做兼容，不需要为「旧个体没有 ancestors」写特殊分支。
- **风险**：中。主要是 UI 要同时展示「代数/父母编号」，否则玩家看不懂为什么被扣。

### D. 繁育结算策略化（P2，**默认不建议**）

**目标**：让条满不再 100% 出蛋。

```
成功率 = clamp(0.55 + 0.25 × 承担方耐受比例 + 0.05 × (交集蛋组数 − 1) + 等级修正, 0.35, 0.95)
失败：不产蛋，承担方 −12 耐受，清条，提示「这次没配上」
```

**为什么标 P2**：

- 直接推翻"条件成立必出蛋"的确定性设计，`test-logic.mjs:560-734` 里至少 6 条断言会失效（575/610/630/721…）。
- 与"博士只能靠试"叠加后，玩家会更难建立因果认知。
- 若主线确实需要"更耐玩"，更稳的做法是**先把 C 包（亲缘）做完**，用近亲惩罚制造策略，而不是加随机。

若要做，建议同时升 `SAVE_VERSION` 并在帮助文本里明示概率区间。

### E. 孵化器与蛋的交互（P1-6、P2-1、体验）

#### E1 已有蛋也享受孵化器加速（**需拍板**，见 D3）

现状 `total` 在造蛋时冻结（logic.mjs:584），升级只影响之后造的蛋。可选：

- **E1a 不动**：保持现状，只在帮助文本写明。
- **E1b 按比例重算（推荐）**：升级时对每枚蛋做 `daysLeft *= (1−0.1×newLvl)/(1−0.1×oldLvl)`、`total` 同比缩放，向上取整到 0.1 天。约 8 行，`buyUpgrade` 里加一个 `rescaleEggs(state, oldLvl, newLvl)`。

#### E2 蛋卡信息补全

在 [ui.mjs:657-667](../js/ui.mjs#L657-L667) 的蛋卡里补：

- `来源：xxx`（数据已有，纯展示）
- `父母：#0042 × #0057` 或 `父母：培育栏自产`（依赖 C1）
- `还需 3.2 天（共 5.0 天）`

**测试影响**：test-ui.mjs:106 只约束**货架**不显示「孵化 」，蛋卡加天数是安全的；但蛋卡的 `ensureEggs` 签名要同步加 `source/parents`，否则不刷新。

#### E3 蛋位满的引导

`#egg-hint` 改为 `3/3 枚蛋 · 已满`，并在培育页顶部给一条可点击「去升级孵化器」的提示（跳 `tab=market` 并高亮设施）。

#### E4 丢弃/出售蛋（**需拍板**，见 D4）

蛋位满了又不能丢，只能干等孵化。可选「花 6 资金处理」像遗体一样腾位，或直接丢弃。建议**只做丢弃，不做回钱**（避免刷钱路径）。

## 4. 推荐路线

```
批次 1（P0 + 契约）        批次 2（体验）            批次 3（机制）
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ A1 价格表        │   │ F1 状态机        │   │ C1 亲缘数据      │
│ A2 喂食器        │──▶│ F2 动画重放      │──▶│ C2 判定 + K2 惩罚│
│ A3 跨 tick 补结算│   │ F5 researched    │   │ C3 家谱 UI       │
│ A4 兜底/封装     │   │ E2 蛋卡信息      │   │ E1 已有蛋加速    │
│ B  penOutcome    │   │ E3 蛋位满引导    │   │ F3 栏位移动       │
└──────────────────┘   └──────────────────┘   └──────────────────┘
```

**为什么这个顺序**：

1. 批次 1 全是"现有规则没生效"，改完立刻能感觉对；且 B 包是 F1 的前置。
2. 批次 2 是玩家每天看到的东西，收益最直观；不碰数值，风险低。
3. 批次 3 才开始加新机制，此时数据层（亲缘）与 UI 层（状态机）都已经就绪。

**每批结束都要**：`npm test` 全绿 + 浏览器里用 `__game.fastForward(30)` 手动过一遍。
